# mqtt-line-transport Specification

## Purpose

Publishes the raw PLC process image over MQTT from the PC next to each conveyor line, so that a central dashboard can subscribe to any line's broker and receive fresh, trustworthy snapshots with clear liveness semantics.

## Requirements

### Requirement: Publisher reads the process image and publishes snapshots
The line-PC publisher SHALL connect to its S7-1200 PLC read-only (PUT/GET, no writes), read the process image at the configured poll interval (~500 ms), and publish a snapshot message to the line's state topic after each successful read. If the PLC read fails, the publisher SHALL NOT publish a snapshot for that cycle and SHALL retry on subsequent cycles.

#### Scenario: Snapshot published at cadence
- **WHEN** the publisher is connected to both the PLC and the broker
- **THEN** a snapshot message is published to `plc/<line-ip>/state` approximately every poll interval

#### Scenario: PLC read failure does not publish
- **WHEN** the PLC is unreachable or a read fails
- **THEN** no snapshot is published for that cycle and the publisher retries without crashing

#### Scenario: PLC access stays read-only
- **WHEN** the publisher communicates with the PLC
- **THEN** it only reads the process image and never writes any value to the PLC

### Requirement: Snapshot payload format
Each snapshot SHALL be a JSON object containing: `plc_ip` (the PLC's IP address identifying the line), `ts` (a UTC ISO-8601 timestamp generated by the publisher at read time), `inputs_hex` and `outputs_hex` (the raw input and output process-image bytes encoded as hexadecimal, two bytes each covering I0.0–I1.7 and Q0.0–Q1.7). The payload SHALL NOT apply tag semantics; tag names, addresses, and polarity remain the dashboard's responsibility.

#### Scenario: Payload decodes to the process image
- **WHEN** the dashboard decodes a snapshot's `inputs_hex` and `outputs_hex`
- **THEN** each tag in `plc_tags.csv` resolves to the same boolean value the publisher read from the PLC

#### Scenario: Payload identifies the line and read time
- **WHEN** a snapshot is received
- **THEN** its `plc_ip` identifies the line and its `ts` reflects the publisher's read time in UTC

### Requirement: Topic layout
The publisher SHALL publish snapshots to `plc/<line-ip>/state` and liveness status to `plc/<line-ip>/status`, where `<line-ip>` is the PLC's IP address. The status payload SHALL be the literal strings `online` or `offline`.

#### Scenario: Topics are line-scoped
- **WHEN** multiple line PCs publish simultaneously
- **THEN** each line's snapshots and status appear only under its own `plc/<line-ip>/` topic prefix

### Requirement: Retained snapshots
Snapshot and status messages SHALL be published with the MQTT retain flag set, so that a newly connected subscriber immediately receives the latest snapshot and status without waiting for the next publish cycle.

#### Scenario: Late subscriber gets instant state
- **WHEN** the dashboard subscribes to a line's topics
- **THEN** the latest retained snapshot and current retained status are delivered immediately

### Requirement: Last Will and Testament
The publisher SHALL register a Last Will and Testament publishing `offline` (retained) to `plc/<line-ip>/status`. The broker SHALL publish the will when the publisher loses its broker connection unexpectedly. The publisher SHALL publish `online` (retained) after connecting and `offline` (retained) on clean shutdown.

#### Scenario: Publisher crashes
- **WHEN** the publisher process loses its broker connection without a clean disconnect
- **THEN** the broker publishes retained `offline` to the line's status topic

#### Scenario: Clean shutdown
- **WHEN** the publisher is stopped gracefully
- **THEN** it publishes retained `offline` to the line's status topic before exiting

### Requirement: Broker without authentication
The line-PC broker SHALL accept MQTT connections without a username or password on its configured TCP port (default 1883) and SHALL deliver QoS 0 and QoS 1 messages, retained messages, and Last Will and Testament messages.

#### Scenario: Anonymous client connects
- **WHEN** the dashboard connects to a line's broker without credentials
- **THEN** the connection succeeds and subscriptions receive published messages

### Requirement: Local Python broker
The broker SHALL run as a pure-Python component installed in the project virtual environment, started by its own entrypoint on the line PC, and SHALL log connection and disconnection events.

#### Scenario: Broker starts on the line PC
- **WHEN** the broker entrypoint is started with its configured port
- **THEN** it accepts MQTT client connections and runs until stopped
